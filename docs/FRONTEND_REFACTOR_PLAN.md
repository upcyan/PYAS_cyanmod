# 前端重构方案:WinUI 3 双前端

> 状态:**方案稿(未实施)**。本文只做选型、边界、分期与验收设计;不含已落地的代码改动。

## 1. 现状与约束(可核对的事实)

| 项 | 现状 |
|---|---|
| UI 技术栈 | pywebview 6.x → WinForms 宿主 + WebView2,HTML/CSS/JS 由本地 HTTP 提供 |
| 前端规模 | `Interface/` 共 **12,746 行**:JS 5,287(i18n 4,770 + main 3,356 + threat 477 + policy 180)、HTML 1,353、CSS 2,591 |
| 页面 | `index.html` 里 **18 个 page/sub-page** + 威胁弹窗 + 通知窗 |
| 桥接 | pywebview `js_api`(同进程对象),JS 侧调用 **54 个** `pywebview.api.*` 方法 |
| 后端 | 同一进程 `WindowAPI(MainMixin, ScannerMixin, ToolsMixin, ProtectMixin)`;策略写入走 `_policy_call`(需管理员授权) |
| 本地服务 | `127.0.0.1:0` 随机端口,**只提供静态文件**,不暴露 API |
| 打包 | PyInstaller onefile + Inno Setup,当前 **75.2 MB**;己方组件靠 `is_own_process_image`(同目录 + 已知文件名)放行 |

**关键结构性事实**:UI 与引擎是**同一进程内的对象调用**。WinUI 3 无法从 Python 侧直接实例化,必须拆成**独立进程 + 显式契约**——这一步才是一切风险与工作量的来源,而不是"重画界面"。

## 2. 选型与取舍

| 候选 | 观感 | 与现有引擎集成 | 交付体积 | 维护成本 | 结论 |
|---|---|---|---|---|---|
| **WinUI 3(Windows App SDK)** | 原生 Fluent,最接近系统设置页 | 需新增进程与 IPC;后端不动 | 框架依赖 +~50 MB / 自包含 +~120 MB | 双 UI 并行 | **采用(可选前端)** |
| WPF | 原生控件但非 Fluent | 同上 | +~60 MB | 同上 | 备选:若 WinUI 3 在无包部署上踩坑,可降级到 WPF 且契约层不变 |
| 继续 WebView2 | 现有观感 | 零改动 | 0 | 最低 | 保留为默认,直到 WinUI 达到功能对齐 |
| Tauri / Electron | 仍是 Web | 需重做壳 | 更大 | 中 | 无收益 |
| 全量 C# 重写引擎 | — | 重写驱动/策略/YARA 集成 | — | 极高 | **否决**:安全能力不可承受重写风险 |

**为什么是 WinUI 3**:用户要求"原生观感 + 与系统一致";WinUI 3 是当前唯一能做到 Fluent 原生控件、且能独立进程承载的方案。**代价**如实列出:

1. 多一个运行时依赖(Windows App SDK + .NET 8),安装包与体积上升;
2. 两套 UI 要同步功能,长期是双倍回归面;
3. 无包(unpackaged)WinUI 3 需自建单实例、启动引导与自保护,踩坑点多;
4. 新增一个 exe → 必须进入**签名 + 白名单 + 自保护**链路(上次启动器被自己拦截就是先例)。

**取舍结论**:WinUI 3 作为**可选前端**,默认仍是经典 UI;设置项 `ui_frontend = classic | winui`,由启动器决定拉起哪个客户端。**引擎、策略、检测、驱动一律不动**,这样回退只需切一个开关。

## 3. 目标架构

```
┌───────────────┐   ┌───────────────┐
│ 经典 UI(HTML)│   │ WinUI 3 客户端 │   ← 二选一,同一个后端
└──────┬────────┘   └──────┬────────┘
       │  js_api(进程内)   │  命名管道(ACL + 令牌 + 客户端校验)
       └─────────┬─────────┘
            ┌────▼─────────────────────────┐
            │ 引擎进程 PYAS.exe             │
            │ WindowAPI → 策略/检测/AI/驱动 │
            └──────────────────────────────┘
```

**契约层先做**:把 54 个 `js_api` 方法收敛成一份版本化接口(`docs/api/local-api.md` + JSON Schema),经典 UI 通过 JS shim 走同一份定义,WinUI 走命名管道。

- **选命名管道而不是 HTTP**:HTTP 端口任何本机进程都可连;命名管道可设 ACL(仅当前用户)、可校验客户端 PID 与会话,配合一次性令牌,防止别的程序冒充弹窗做"允许"决策。
- 破坏性变更一律走版本号:`X-PYAS-Api: 1`。

## 4. 安全能力保全(硬性要求,验收即按此判)

| 能力 | 保全方式 | 验收判据 |
|---|---|---|
| 策略需管理员授权 | 新 API 只能调用 `_policy_call`,不得直写配置 | 无授权时写策略必须失败,且界面显示明确失败原因 |
| 告警决策不可伪造 | 决策接口绑定 `alert_id` + 管道客户端校验 | 伪造管道客户端发 `allow` → 拒绝并记日志 |
| 密钥不外泄 | 密钥只在引擎侧解密;UI 只拿脱敏视图 | 抓包/转储 UI 进程内存不得出现明文 key |
| 日志完整性 | 仅引擎可写日志;客户端只读 | 客户端崩溃/篡改不影响日志落盘 |
| 自保护 | 新 exe 进 `is_own_process_image` + 白名单 + 签名 | 启动新前端不触发自身拦截;未签名副本被拦 |
| 防护不因 UI 退出而停 | 引擎与 UI 解耦 | 杀掉 UI 进程,文件/进程防护仍生效 |
| 降级可用 | 经典 UI 永远保留 | 切回 classic 后功能与现在逐项一致 |

## 5. 分期与交付物

| 阶段 | 内容 | 产出 |
|---|---|---|
| P0 | 契约层:接口清单、JSON Schema、命名管道服务端、鉴权 | `docs/api/local-api.md`、`PYAS_ApiServer.py`、契约测试 |
| P1 | 经典 UI 改走契约层(行为不变) | JS shim + 回归全绿;这是双前端的**前提** |
| P2 | WinUI 3 客户端骨架:单实例、自绘标题栏、主题、导航 | `PyasUi/` 项目 + 能连上 P0 |
| P3 | 功能对齐:首页 → 日志 → 隔离区 → 扫描 → 设置 → 策略 → 威胁弹窗 | 逐页 parity 清单 |
| P4 | 设置项 + 启动器路由 + 安装包组件化 | `ui_frontend` 开关;安装可选组件 |
| P5 | 加固与验收 | 验收报告(见下) |

**不在本次范围**:引擎、检测规则、驱动、策略存储格式、更新协议。

## 6. 测试与验收方案

**功能**:18 个页面 × 逐项 parity 清单(控件、状态、文案、空态、错误态);关键流程脚本化(扫描→告警→决策→隔离→放行)。

**安全回归**(每次构建必跑):
1. 策略写入无授权 → 拒绝(现状已有 `test_policy_*`,扩到新 API);
2. 管道客户端未通过 PID/令牌校验 → 全部拒绝;
3. 伪造告警决策 → 拒绝 + 审计日志;
4. UI 进程被 kill → 防护仍在(用 EICAR 自测串验证);
5. 未签名/改名副本启动 → 被自身拦截;
6. 回退到 classic → 全功能回归。

**性能**:冷启动、内存、告警弹窗首帧、日志列表 1000 条滚动帧率;与经典 UI 对比,劣化 >20% 视为不通过。

**验收标准**:功能 parity 100%(有清单逐项签字)、安全回归 6/6 通过、无高危缺陷、回退演练成功。

**回滚**:设置切回 `classic` 或安装包回退;引擎未改动,回滚不影响数据与策略。

## 7. 风险与前置问题

1. **体积**:自包含 .NET 会让安装包从 75 MB 涨到 ~200 MB,需先定形态;
2. **双 UI 长期维护**:需明确"经典 UI 冻结新功能"还是继续跟进;
3. **签名**:新 exe 是否一并进现有签名/白名单链路(影响内测包与自保护);
4. **WinUI 3 无包部署**的单实例与启动引导,需要一轮真机验证后再定 P2 的具体做法。
